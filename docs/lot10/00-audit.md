# Lot 10 (Aurore Mobile) — Audit préalable du code réel

Lecture seule — aucun fichier applicatif modifié par ce document. Chaque affirmation cite un chemin réel ; tout ce qui n'a pas pu être vérifié est marqué **introuvable**.

## 1. Serveur

- **Point d'entrée** : `backend/src/index.ts`. Démarrage en deux temps : d'abord `DATABASE_MODE` (portable/externe) est résolu et, en mode portable, Postgres portable est démarré et `process.env` est complété (secret de session, clés API embarquées) — **avant** tout `import` de `./config/env` ou `./app` (chargés dynamiquement via `await import(...)`, lignes 216-235). Ordre volontaire : `config/env.ts` valide `process.env` une seule fois, au chargement du module, et met le résultat en cache pour tout le process (piège documenté lignes 124-151).
- **Montage Express** : `backend/src/app.ts`. Un seul `express()` (`app`), tous les routeurs sont montés **sans préfixe** sur cette même instance (`app.use(xxxRouter)`), chaque routeur déclarant ses propres chemins complets (`/api/...`). `app.set("trust proxy", 1)` (ligne 62, nécessaire derrière Traefik en mode VPS). Taille max du corps JSON : **30 Mo** (`express.json({ limit: "30mb" })`, ligne 75) — limite de transport, pas la limite métier réelle par fichier (`DOCUMENTS_TAILLE_MAX_MO`, vérifiée après décodage côté route).
- **Interface d'écoute** (`index.ts` lignes 237-303) :
  - Mode portable + `deploymentMode === "standalone"` (poste unique) : `app.listen(env.PORT, "127.0.0.1", ...)` — jamais exposé au réseau.
  - Mode portable + `deploymentMode === "reseau"` (Lot 6) : **deux serveurs** — un serveur **HTTPS** (certificat auto-signé local, `security/localTlsCertificate.ts`) qui bind `0.0.0.0:env.PORT`, **et** un second serveur HTTP simple sur `127.0.0.1:(env.PORT+1)` réservé à la fenêtre Tauri locale elle-même (qui ne sait pas parler HTTPS auto-signé). `env.PORT` par défaut 3000.
  - Mode externe (VPS) : `app.listen(env.PORT, env.HOST, ...)` — comportement historique, `env.HOST`/`env.PORT` viennent de `.env`.
  - `deploymentMode` est lu depuis `%APPDATA%\Aurore\config.json` (écrit par `config/deploymentMode.ts`), jamais depuis une variable d'environnement — repli sûr sur `"standalone"` si absent/corrompu.
- **Authentification** : `backend/src/middleware/requireAuth.ts`. **Cookie** `aurore_session` (JWT, voir `services/auth.ts`), jamais d'en-tête `Authorization`. Revérifie à chaque requête que le compte est actif et que le cabinet est actif/non expiré. **Aucun mécanisme de jeton par appareil n'existe aujourd'hui** — le protocole d'appairage mobile (Prompt 1) doit être une brique d'authentification entièrement nouvelle, parallèle à celle-ci, pas une réutilisation.
- **Rôles** : `backend/src/middleware/roles.ts` — `requireAdmin` (titulaire seul), `requireAvocat` (titulaire+avocat), `requireModule(cle)` (vérifie `Cabinet.modulesDesactives` PUIS `User.modulesDesactives`, jamais l'inverse — un module coupé par la plateforme ne peut jamais être réactivé par un titulaire).
- **Limitation de débit** : `backend/src/middleware/rateLimit.ts` — par IP (pas par compte), trois limiteurs : connexion (10/15 min), actions IA (60/15 min), général (`globalApiLimiter`, 600/15 min, appliqué à tout `/api/*` dans `app.ts` ligne 76).
- **Clé publique des modules payants** : `backend/src/config/modulesDisponibles.ts` — liste fermée (`MODULES_DISPONIBLES`), toute autre clé est rejetée par Zod. `"mobile"` n'existe pas encore : à ajouter ici si le Prompt 1 veut un module désactivable séparément (voir risque R2).

## 2. Données

- **Schéma** : `backend/prisma/schema.prisma` (1638 lignes). Migrations hand-written sous `backend/prisma/migrations/<timestamp>_<nom>/migration.sql`, régénérées en SQL "init complet" via `npm run prisma:portable-sql` → `prisma/portable-init.sql` (sert uniquement à la toute première installation d'un cabinet) ; les migrations existantes sont réappliquées aux installations déjà en place par `applyPendingMigrations.ts`.
- **Convention de nommage** : noms de champs/modèles Prisma en **français** (`nomAffaire`, `createdBy`, `supprimeLe`...), mappés en snake_case anglais-neutre côté colonnes SQL réelles via `@map(...)` (ex. `createdBy` → `created_by`). `cabinetId` est présent sur quasiment tous les modèles métier (isolation stricte par cabinet) — à reproduire sur `MobileDevice`/`MobileItem`.
- **Convention "jamais de cascade"** : confirmé nulle part dans le schéma un `onDelete: Cascade` sur une relation métier (seules deux exceptions techniques : `EvenementAssigne.evenement` et `EvenementSyncExterne` en `SetNull`). Une suppression définitive supprime toujours les lignes dépendantes explicitement, dans l'ordre, en transaction (voir `jobs/purgeCorbeille.ts` comme gabarit).
- **Dossier** (`schema.prisma:591`) : `id`, `cabinetId`, `clientId?`, `numeroDossier`, `nomAffaire`, `nomClient` (dénormalisé), `createdBy`, `statut` (`"actif"`/`"cloture"`, chaîne libre pas un enum), `estRecherche` (dossiers "fiches de recherche", pas de vrais dossiers client), `dateCloture?`, `archivedAt?` (archivage auto après clôture), `supprimeLe?`/`supprimeParId?` (corbeille, 30 jours). Relations : `actions`, `delaiCalculs`, `factures`, `roleAudiences`, `evenements`, `saisiesTemps`, `documents` (`DocumentDossier[]`), courriers entrants/sortants.
- **Client** (`schema.prisma:483`) : `id`, `cabinetId`, `nom`/`email`/`telephone` (**chiffrés au repos**), **pas de `createdBy`** — un client est partagé par tout le cabinet sans notion de propriétaire (confirmé : `routes/clients.ts` ne filtre jamais par `getAccessibleAvocatIds`).
- **Calendrier/Audience** : vue unifiée `Evenement` (`schema.prisma:904`, Lot 12a) — `type` (`audience`/`rdv`/`appel`/`tache`/`echeance_procedure`/`autre`), `source` (`manuel`/`role_audience`/`delai_calcule`/`sync_google`/`sync_caldav`/`email`), `dossierId?`, `createdById`, `visibilite` (`prive`/`equipe`/`cabinet`, ajouté 2026-10-08). Les types `audience` et `echeance_procedure` ne sont **jamais** créés directement via `POST /api/evenements` — uniquement générés depuis `RoleAudience`/`DelaiCalcul` (`services/evenementSync.ts`). `RoleAudience` (`schema.prisma:867`) a son propre modèle riche (juridiction, chambre, parties, diligences...), `dossierId` **optionnel**.
- **Délai** : `DelaiType` (gabarit réutilisable : nombre d'unités, unité, jours ouvrés ou non, texte de référence légale) + `DelaiCalcul` (instance : `dateDepart`, `dateLimite` calculée, `dossierId?` optionnel, `courrierEntrantId?` optionnel — précédent direct pour "Créer un délai depuis un scan").
- **Courrier** : `CourrierEntrant` (`schema.prisma:1507`, statuts **`recu → a_affecter → affecte → en_traitement → traite → classe`**) et `CourrierSortant` (`schema.prisma:1550`, statuts `brouillon → envoye → classe`). **Il n'existe pas de statut littéral `"a_traiter"`** — voir risque R1, le Prompt 2 suppose ce libellé. Création programmatique : `services/courriers/courrierService.creerCourrierEntrant(cabinetId, userId, input)` (statut initial toujours `"recu"`, jamais choisi à la création) ; affectation : `affecterCourrierEntrant(id, cabinetId, affecteAId)` (route `POST /api/courriers-entrants/:id/affecter`, `routes/courriers.ts:151`) — limité aux rôles `titulaire`/`avocat`/`collaborateur` actifs du même cabinet, envoie aussi un email de notification.
- **Action** (`schema.prisma:1236`) : `typeAction` (`notes` = **compte-rendu d'audience**, `redac`, `conclusions`, `assignation`...), `dossierId` (**obligatoire**, pas nullable), `contenuGenere` (chiffré au repos), `dateAudience?`, `prochaineAudience?`, `createdBy`, `verrouillePar?`/`verrouilleLe?` (verrou d'édition Lot 11), `courrierEntrantId?` (chaînage courrier→action), `supprimeLe?`/`supprimeParId?` (corbeille).
- **Journal d'audit** : `AuditLog` (`schema.prisma:1429`) est **étroitement scopé** : `actionId?`, `courrierEntrantId?`, `courrierSortantId?` — **aucun `cabinetId` propre, aucune notion d'événement générique** (type "appairage demandé" n'a pas de table d'accueil naturelle). Voir risque R3.

## 3. Fichiers

- **Documents de dossier (GED)** : `backend/src/services/stockageDocuments.ts`. Chiffrement **AES-256-GCM** par fichier (pas seulement par champ), format sur disque `IV (12o) || AuthTag (16o) || ciphertext`, nom de fichier physique = UUID aléatoire (`.enc`), jamais le nom d'origine. Réutilise **la même clé** que le chiffrement de champs texte (`security/encryptionAtRest.ts`, `loadOrCreateEncryptionKey()`) mais avec des fonctions binaires dédiées (un buffer binaire n'est pas de l'UTF-8 valide). Stockage sous `userDataDir()/documents/<dossierId>/<uuid>.enc`.
- **Clé de chiffrement** : `security/encryptionAtRest.ts` — AES-256-GCM, clé 32 octets, priorité à `AURORE_ENCRYPTION_KEY` (env) puis génération locale dans `secretsDir()/encryption-key.json` (permissions restreintes via `icacls` sous Windows). **Une clé par installation, jamais partagée entre cabinets.**
- **Dossier de données** (`backend/src/database/portablePaths.ts`) : `userDataDir()` = `%APPDATA%\Aurore` sous Windows (jamais le dossier d'installation, qui peut être réécrit à la mise à jour). `secretsDir()` = `.../secrets`, `backupsDir()` = `.../backups`. Un futur stockage `MobileItem` devrait suivre le même principe : `userDataDir()/mobile-items/<deviceId>/<uuid>.enc`, et réutiliser `loadOrCreateEncryptionKey()` + le même format binaire que `stockageDocuments.ts` (à généraliser/extraire plutôt qu'à dupliquer, ou dupliquer volontairement comme le fait déjà `stockageDocuments.ts` lui-même vis-à-vis d'`encryptionAtRest.ts` — convention du projet).
- **Sauvegardes** : `backend/src/database/backupScheduler.ts` — `pg_dump` quotidien **plus** mirroring de `documents/`, `secrets/`, `public/uploads` vers `backups/fichiers/` (ajouté 2026-?? après l'audit de risque de perte de données de cette session). Un futur `mobile-items/` devrait être ajouté à ce mirroring pour rester couvert par les sauvegardes nocturnes.

## 4. Front

- **Pas de SPA** : multi-pages HTML statiques servies par `express.static` (`app.ts:125`), chaque page charge `api.js` puis `layout.js` puis son propre `<script>` inline ou un fichier dédié sous `public/js/`.
- **`public/js/api.js`** : `apiFetch(path, options)` (fetch authentifié avec cookie, gestion d'erreur uniforme), `downloadFile(url, fallbackFilename)` (fetch → blob → lien `<a download>` synthétique — **obligatoire** car `<a target="_blank">`/liens de téléchargement directs ne fonctionnent pas dans la webview Tauri), `ouvrirLienExterne(url)` (ouvre dans le navigateur système via le plugin Tauri `opener`, jamais `window.open` seul en contexte Tauri), `requireSession()` (vérifie la session, redirige vers `/login.html` ou `/licence.html` sinon), `confirmerSuppression({...})` (modal de confirmation rouge, obligatoire pour toute suppression dans l'app — convention stricte établie cette session).
- **`public/js/layout.js`** : `NAV_ITEMS` (tableau déclaratif : `href`, `label`, `roles` (quels rôles voient l'entrée), `group`, `icon`, `moduleKey?` optionnel) → `initLayout(me)` construit la sidebar/topbar à partir de ce tableau, filtré par rôle et par `me.modulesDesactives`. **Ajouter une page au menu = ajouter une entrée à `NAV_ITEMS`**, rien d'autre (pas de registre séparé).
- **Ajouter une page** : créer un fichier `public/<nom>.html` (squelette `<head>` + `.page` + scripts `api.js`/`layout.js` + script propre), l'enregistrer dans `NAV_ITEMS`. Pas de bundler, pas de build front : les fichiers sont servis tels quels.
- **`dashboard.html`** ("Documents générés") : utilise `GET /api/documents` (pas `/api/dossiers`), regroupe les résultats par `typeAction`, scope `mine`/`cabinet` + vues (`dossiers`/`recherches`/`traductions`/`transcriptions`/`archives`). **Ne liste jamais les dossiers eux-mêmes** — uniquement vu cette session (ajout de `mes-dossiers.html`, qui réutilise `GET /api/dossiers` directement).
- **`dossier.html`** : fiche complète d'un dossier (onglets Pièces/Actions/Courriers/Agenda...), verrouillage d'édition, confirmation de suppression. Référence pour "rattachement d'un scan au dossier" (onglet Pièces existant, `routes/documentsDossier.ts`).
- **`delais-calculateur.html`** : formulaire de calcul de délai, prend potentiellement un `dossierId` en contexte (à vérifier précisément au Prompt 2 — non audité ligne à ligne ici).
- **`nouvelle-action.html`** : formulaire multi-onglets (un onglet par `typeAction`, dont `"notes"` = compte-rendu d'audience), sélection du dossier via un **champ texte `numero_dossier` avec `<datalist>`** (`name="numero_dossier" list="dossiers-datalist"`), **jamais un `dossierId` direct ni une présélection par paramètre d'URL** (aucun `URLSearchParams`/`window.location.search` trouvé dans ce fichier). Voir risque R4 : "dossier présélectionné" (Prompt 2.B) n'est **pas** un comportement existant, c'est à construire.
- **`envoiActions.js`** : logique partagée d'envoi d'un document généré (email client/collègue/huissier/soi-même), extraite de `dossier.html` pour être réutilisée sur `dashboard.html` — sans lien direct avec Aurore Mobile, mentionné pour mémoire.

## 5. Réseau et installeur

- **Lancement par Tauri** : `src-tauri/src/main.rs`. Le backend tourne comme **sidecar** (process enfant géré par `tauri-plugin-shell`), reçoit `AURORE_APP_ROOT=<resource_dir>` (ligne ~167) pour localiser `public/`/`prisma/`/binaires Postgres packagés. `health_url()`/`app_url()` pointent toujours sur `127.0.0.1`, sur `BACKEND_PORT` (3000) en mode poste unique ou sur `BACKEND_PORT+1` (3001, `LOCAL_SHELL_PORT`) en mode réseau (puisque le serveur principal bascule alors en HTTPS auto-signé, que cette fenêtre ne peut pas accepter silencieusement).
- **Arrêt propre** : écriture de `"shutdown"` sur le `stdin` du sidecar (Windows ne propage pas `SIGTERM` de façon fiable à un process enfant) — voir `index.ts` lignes 383-393.
- **Pare-feu Windows** : **l'installeur NSIS n'ajoute PAS de règle automatiquement.** `installer/firewall-rule.ps1` existe mais est un script **manuel**, à exécuter soi-même en administrateur (confirmé : aucune référence à `firewall-rule.ps1` dans le code applicatif, seulement une instruction textuelle dans `public/setup-mode.html:105`). Ouvre un port TCP unique, profil réseau **Privé uniquement**, idempotent, avec option `-Remove`. Un second serveur mobile sur un port différent (3100 par défaut dans le plan) nécessitera soit un second appel à ce script avec `-Port 3100`, soit son extension pour accepter plusieurs ports, soit son intégration dans l'écran de réglage "Synchronisation mobile" (déclenchement du script PowerShell depuis le backend/l'app, avec élévation UAC — **non trivial**, voir risque R5).
- **Mode réseau existant (Lot 6)** : déjà pensé pour plusieurs postes clients sur le LAN du cabinet (bind `0.0.0.0`, HTTPS auto-signé, annonce mDNS via `network/mdnsAdvertise.ts`). Le serveur mobile (Prompt 1) est une **troisième** interface d'écoute distincte, qui doit cohabiter avec les deux serveurs déjà actifs en mode réseau (HTTPS public + HTTP local Tauri) sans conflit de port.

## 6. Module Courriers

Couvert en détail en section 2 (modèle) et route par route ci-dessus. Résumé opérationnel :
- Écrans : `public/courriers.html` (liste + bouton "Rédiger un courrier"), fiche courrier dédiée (`public/js/courrier-fiche.js`).
- Création programmatique entrant : `courrierService.creerCourrierEntrant(cabinetId, userId, { objet, nature?, expediteur?, dateCourrier?, dateReception?, modeReception?, clientId?, dossierId?, observations? })` — seul `objet` est obligatoire.
- Affectation : `courrierService.affecterCourrierEntrant(id, cabinetId, affecteAId)`.
- Génération du numéro : `services/courriers/numerotation.ts` (séquence atomique par cabinet/année/sens, `SequenceCourrier`).
- Pièces jointes d'un courrier : `CourrierPieceJointe` (modèle séparé de `DocumentDossier`) — **un scan "courrier" depuis le mobile devra décider s'il devient une `CourrierPieceJointe` ou un `DocumentDossier` classé** ; `DocumentDossier.source` (`schema.prisma:667`) accepte déjà `"upload"`/`"email"`/`"courrier"` — ajouter `"mobile"` y est cohérent avec la convention existante si le choix se porte sur `DocumentDossier`.

## 7. Risques (par priorité)

1. **[Majeur] Enregistrement audio en arrière-plan, écran verrouillé, Android.** Déjà identifié par le plan lui-même (Prompt 4, étape 0 obligatoire) — confirmé sans réserve par cet audit : **aucun code mobile n'existe encore**, donc aucune réutilisation possible, tout est à faire et à valider sur du matériel réel, par marque. Point de blocage avant toute suite.
2. **[Majeur] Authentification mobile entièrement nouvelle.** `requireAuth` actuel est 100% cookie/JWT navigateur — il n'existe aujourd'hui **aucun** mécanisme de jeton par appareil, par API key ou OAuth device flow dans le code. Le protocole X25519/tweetnacl du Prompt 1 n'est pas une adaptation d'un mécanisme existant, c'est une brique de sécurité neuve à documenter et faire relire avant codage (déjà prévu par le plan — confirmé nécessaire).
3. **[Moyen] Journal d'audit trop étroit pour les événements mobiles.** `AuditLog` n'a ni `cabinetId` propre ni notion d'événement libre hors `Action`/`CourrierEntrant`/`CourrierSortant`. Un événement "appairage demandé" ou "échec d'authentification" n'a pas de ligne naturelle où s'écrire. **Recommandation** : une table dédiée (`MobileAuditLog` : `cabinetId`, `deviceId?`, `etape`, `statut`, `detail?`, `timestamp`), plutôt que forcer `AuditLog` existant à accepter un cas qu'il n'a jamais prévu.
4. **[Moyen] "Dossier présélectionné" et statut "À traiter" n'existent pas tels que le plan les décrit.** `nouvelle-action.html` n'a aucune présélection par URL aujourd'hui (champ texte + datalist, pas un `dossierId`) ; `CourrierEntrant.statut` n'a pas de valeur littérale `"a_traiter"` (le plus proche est `"a_affecter"`/`"recu"`). Les prompts 2 et 5 devront explicitement ajouter ces capacités plutôt que les "réutiliser" comme supposé — pas bloquant, juste un périmètre de travail plus large que prévu sur ces deux points précis.
5. **[Mineur mais réel] Ouverture du port mobile sur le pare-feu Windows reste un geste manuel aujourd'hui.** Pas d'automatisation existante à réutiliser ; `firewall-rule.ps1` est conçu pour un seul port/usage interactif. À décider : nouveau paramètre `-Port`, ou appel PowerShell déclenché depuis l'écran de réglage (élévation UAC à gérer).
6. **[Mineur] Clé de module "mobile" absente de `MODULES_DISPONIBLES`.** Si le module doit être désactivable par la plateforme comme les autres (facturation, délais, courriers...), il faut l'ajouter à `backend/src/config/modulesDisponibles.ts` (changement additif, un seul endroit, déjà fait pour "corbeille" cette semaine — procédure connue et sûre).

## Questions à trancher avant le Prompt 1

1. **Emplacement du code mobile** : un dossier `mobile/` dans ce même dépôt (monorepo), ou un dépôt séparé ? Le dépôt actuel n'a aucune trace d'un tel dossier aujourd'hui — à créer dans un cas comme dans l'autre. Le risque principal d'un monorepo est que le workflow CI existant (`build-windows-installer.yml`) ne doit jamais être déclenché par un changement purement mobile, et vice-versa (filtrage par chemin à ajouter).
2. **Journal d'audit mobile** : nouvelle table dédiée (recommandé ci-dessus, R3) ou extension d'`AuditLog` existant (plus risqué, touche un modèle partagé par Action/Courriers) ?
3. **Devenir d'un scan "courrier" dans Aurore** : `DocumentDossier` (classé dans la GED du dossier, source `"mobile"`) ou `CourrierPieceJointe` (pièce jointe du courrier lui-même) — ou les deux selon le contexte ?
4. **Licence/module "mobile"** : confirme-t-on qu'il doit être une clé de `MODULES_DISPONIBLES` comme les autres modules payants (contrôlable par la plateforme ET par le titulaire), ou un simple réglage cabinet sans lien avec le système de licence ?
5. **Ouverture du pare-feu pour le port mobile** : geste manuel documenté (comme le mode réseau actuel) accepté pour une première version, ou automatisation (élévation UAC depuis l'app) exigée dès le Prompt 1 ?
